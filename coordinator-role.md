# The role of the coordination session

The coordination session runs in a clone of this repository and runs each run on the information of the workspace it is given (`repo.json`, `coordination.md`). A work session sees only its run worktree and the instructions the coordination session gives it.

An AutoFlow module has only inputs, outputs and defaults, and ends when it reaches its goal. A module does not fix how its result is used, but the next module cannot run without its inputs. What comes after (reruns, counts, timeouts, dispositions) is the coordination session's job. A session opened in a clone of this repository is a coordination session: it builds a workflow that fits the request, assembles its modules, opens work sessions in terminal surfaces that do the work by running those modules, composes each output to fit the next input, judges the result and connects it to what comes next.

Goal: the coordination session completes the issue it is given, to the final result its workflow ends at ([Composition and verdict](#composition-and-verdict)). Feedback on that result is a cause for re-entry ([Composition and verdict](#composition-and-verdict) > Re-entry). The decisions it makes on the way and the limit at which it stops are set in [Operator boundary](#operator-boundary).

Mechanical behavior runs without AI, through JSON settings and tools; judgment belongs to the coordination session. This document sets the goals and concepts of that role, and the coordination session judges each case in light of them. What is already settled is read from its source of truth in the table below.

| What to know | Where to look |
|---|---|
| The modules there are | `tools/modules.py`: each module's `name`, `goal`, `description`, the path of its `SKILL.md`, its location (`default` or `user`) and, for a user module that replaces a default module, `replaces`, that default module's `SKILL.md` path |
| A module's goal, inputs, exit, outputs and defaults | The module's `SKILL.md` |
| Reference workflows | [workflows/README.md](workflows/README.md) |
| The applied settings and paths, read from `tools/config.py`; the work space (the workspaces and run worktrees under the base, and a base the operator has confirmed); the progress records (run data `<runs>/<run name>/` and record folders under the coordination root); where user values go | [SETTINGS.md](SETTINGS.md) > Order in which settings are found, Work space, Progress records |
| A workspace: finding one, checking `repo.json`, reading and following `coordination.md`, building one with the operator when it does not exist, the token every session of it uses as `GH_TOKEN` and with which the coordination session is started; where per-repository values and instructions go | [WORKSPACE.md](WORKSPACE.md) > Finding, Creating, `repo.json`, `coordination.md`, `gh-token` |
| Run preparation; a module run's work folder, invocation, instruction file and end record; starting, instructing, watching and ending sessions; checks; totals | [Tools](#tools), `tools/` |

The two locations a run's modules are taken from, and the names under which `run.env` records them, are in [SETTINGS.md](SETTINGS.md) > Module locations. Read a module's `SKILL.md` in the run's `MODULES` or `USER_MODULES`, the location `tools/modules.py` shows for it, when writing its invocation: these are the locations `tools/invocation.py` takes it from.

## Module connection

Goal: the next module receives every input it needs to run, as the Input section of its `SKILL.md` names them. A `SKILL.md` names its inputs and does not say what they come from. The coordination session composes them from this run's actual files and values and gives them, with the instructions, through `tools/invocation.py`: each input under the name the Input section gives it, as a string or an array of strings. `tools/invocation.py` does not check the inputs against the module, so the coordination session confirms that every required input is given and that its content is right. Outputs are read and judged by their content; no tool checks a heading, wording or line format in them.

`tools/invocation.py` makes each module run's work folder, where the coordination session reads that module run's outputs, and prints the module run's name and the paths: the name, and where the work folder, the invocation, the instruction file, the end record and a file made as an input go, are in [SETTINGS.md](SETTINGS.md) > Progress records. It stops, making nothing, when the record folder's path is too long for the line `tools/session.py send` enters for that instruction file to fit one terminal message: set a shorter `root` ([SETTINGS.md](SETTINGS.md)).

- **Match by meaning**: an output's name and an input's name can differ. Match by whether the content is what that input requires.
- **Extract values**: if a needed value is inside an earlier output, read it and give the value itself as the input.
- **Make a missing input**: if the earlier step did not run or the needed content is not in the output, the coordination session makes the input with the content the module's Input section asks for. The source of an input it made is left in the run record.
- **Ask the session**: if an earlier output is not enough to compose the next input, the coordination session can ask the session that produced it for more work or material while that session is alive. The coordination session judges whether to make the input itself or ask the session.
- **Split and collect**: if one output calls for a module run per item, split the module runs per item, and when all have ended, collect their outputs into the next input. The coordination session confirms no item is missing.
- **Criterion decisions**: criterion decisions are written to and read from the criteria block of the issue, through `tools/criteria.py`. A criterion decision that changes a criterion's content is appended before it reaches a later module, each decision in its own call: revised is `--revise N`; excluded is `--withdraw N`; added is `--add` with a number the block does not use; split is `--revise N` with the first criterion's text and one `--add` per further criterion, in one call. The run record holds the numbers given and the module's ids they stand for. A decision that keeps the criterion writes no line, and the run record names its decision record. On an issue with no block, the coordination session seeds the block before the first criterion decision, in one call: one `--add N` line per acceptance criterion of the issue, numbered from 1 in the order the issue states them, with the issue's text. Every later decision, and every module's criterion decisions, uses those numbers. A module's criterion decisions are composed from the accepted criteria, block number N being the issue's N-th criterion: a revision is revised, a withdrawal excluded, a new number added, and a later line supersedes an earlier one. A revision of a criterion that another revision set takes a fact the earlier grounds comment does not state. A grounds comment states what did not hold, how it was checked (one command and its result) and what changed, and names the details by their path relative to the run's record folder. For a criterion-decision run's decision it is written from the decision record's grounds, command and result.
- **Compare the criteria**: at each module transition, before the module run that opens the PR and before starting the merge session, the coordination session runs `tools/criteria.py read` and compares the block with `seen`, the state it last accepted: the last revision line, new lines, accepted lines removed or edited, and effective texts that changed. A run's first `read` has no `seen`, so every line is a difference. On a difference, it assesses the impact, decides whether to accept it, reviews the re-entry point, records the state with `seen` and continues.
  - A new line is accepted only when `read` attributes it to the workspace account; an unlinked line by the account is the operator's revision. Untrusted lines, accepted lines removed or edited, effective texts that fell back or disappeared, and the overwritten edits the tool reports go to the operator report.
  - Accepting a removed or edited accepted line is `seen --drop` naming the line, with the grounds in the run record. Not accepting it is restoring it before the next module: `append --drop` naming the line, with the line the number's accepted effective state requires (`--revise` with the accepted text, `--withdraw`, or `--add` when no line of the number is left) and a grounds comment naming the line and the login and time `read` gave. A removal or edit that leaves the number's effective state unchanged needs no line. A restoring line that is not confirmed present leaves the removed line in `seen`, so the next `read` reports it again.
  - A line by another login becomes a criterion only through a line by the account: the operator's own unlinked line, or a line the coordination session appends whose grounds comment gives the operator's decision, verbatim, from the run record. A line `read` cannot attribute becomes a criterion only when the coordination session appends its text again, with a grounds comment naming the line and why it could not be attributed.
- **Fill a rerun's inputs**: when the module's Input section names inputs a rerun takes, such as an earlier output or the findings to answer, give them under the names it gives them: the module reads the purpose of this module run from its inputs, and the instructions carry only what Composition and verdict > Instructions sets. Which findings to pass is decided by their disposition (Composition and verdict > **Disposition**): the findings disposed of as fix. When an evaluation or the review is run again, including to check a fix (Composition and verdict > **Checking a fix**), it is given its earlier output under the name that takes it.
- **Collect across module runs**: a module run knows only its own output. What an output reports beyond the module's goal, such as a tool or permission the module run needed and did not have, concerns the run: collect it from all the module runs of the run, give it to a later module whose Input section asks for it, and put it in the operator report.
- **Re-enter from a stop output**: a module run can output the reason it stopped instead of its goal. From that reason, the coordination session judges the step where the cause arose, and composes the content as an input of the module to return to. Even if the Input section of that module names no input that takes that output, match it by meaning or make the input.

## Judgment at each connection

A contract's `from` says only what an input comes from. Below is what that cannot tell, which the coordination session judges at each step, and why. Module names, inputs and outputs below are those of the AutoFlow version in `VERSION`; where the run's AutoFlow version differs, that version's contracts decide.

- **criterion-screen → criterion-in-depth → criterion-reconcile**: how many times in-depth runs is not in the contract but in screen's `targets`. The coordination session splits the module runs per target, sets the `criterion` param, and collects all the results for reconcile. reconcile's `in_depth` is an optional input, so check-in cannot stop a missing one. in-depth must judge without seeing earlier verdicts, so nothing beyond the target is passed in the instructions.
- **criterion-reconcile → criterion-decision → analysis**: a decision that changes a criterion's content (revised, split, excluded or added), and an item on a criterion that the criteria review left undecided, is made by a criterion-decision module run, and the coordination session follows it. A point comes from the criteria review: a disposition that changes a criterion's content, or an item it left undecided. A module run's stop output that records a criterion shown wrong, and a finding that would change what a criterion requires, are causes to re-enter the criteria review, with that output or finding as its input. Each run gets a new session. The points are given as the output that records them states them, with where they are, and without the coordination session's own conclusion. Points whose decisions depend on each other go in one run; a point that stands apart goes in a run of its own; a further point a decision record names goes to a new run. The coordination session checks the facts the decision record states (a commit, a command's result, a file) with git, gh and the command. When they hold, it records the decision as the record states it (Module connection > **Criterion decisions**). When one does not hold, it runs the module again with that fact as an input. After the criteria block changes, criteria-apply runs (Judgment at each connection > **analysis → criteria-apply → hypothesis → design**) and the run goes on to the stage after it. When the criteria review was entered again from a later module, the run returns to that module with the criterion decisions. `criterion_review` and `decisions` are optional inputs, so analysis runs without them. Without them, the result of the criterion review is thrown away. The coordination session gives reconcile's record as the criteria review record and the criterion decisions composed from the criteria block (Module connection > **Criterion decisions**).
- **analysis → criteria-apply → hypothesis → design**: if analysis concluded that no change is needed or that code is not the means, the premise for design and implementation is gone. The coordination session looks at the grounds of that conclusion through hypothesis, judges the remaining groups again, and if the workflow changes, changes it on that judgment as in [Composition and verdict](#composition-and-verdict). design runs with just the evaluation file regardless of hypothesis's scores, so the coordination session disposes of hypothesis's findings (Composition and verdict > **Disposition**) and decides from that disposition whether to run analysis again or go on to design.
- **plan → build**: whether to go on from plan is the same judgment, on the disposition of plan's findings. build's `branch` comes from no output, so the coordination session gives `BRANCH` from `run.env`.
- **build → audit or design**: if build output that it cannot implement the design as is (`green_blocker`), connect it to a design rerun and a plan re-score and then back to build, even if the module run is `accepted`; audit takes the build that implements the design. If `from` and `to` in `commits.json` are the same, there is no commit, so read the reason and decide.
- **build rerun → audit, quality, delivery**: a rerun's `commits` holds only the range that rerun made. For each input, judge whether that range is enough or it must point at the whole change, and make it in the contract's format if needed.
- **audit → quality → delivery**: an evaluation gives scores and findings and does not dispose of them. The coordination session disposes of each finding as Composition and verdict > **Disposition** sets. What is fixed goes to the rerun's `findings`; what is deferred, including what is split into a separate issue, is written by the coordination session in a `deferred` file and passed to the modules that take it; what is rejected stays in the run record with its grounds. `quality_evaluation`, `tool_requests` and `deferred` are optional inputs of delivery, and without them what the operator would see in the PR body is missing.
- **delivery → ci**: a verdict that CI did not run is not a pass. The coordination session judges whether that change meets the quality goal. Even if a ci module run is `failed`, read the verdict in its output.
- **delivery, ci → review**: `delivery.json` can hold several PRs, and review takes one PR per module run. The coordination session splits the module runs per PR and extracts that PR's value into the `pr` param. A re-review is told apart by giving that PR's previous report as `previous_findings`. The findings, with their severity and judged weight, and the head the review saw are read from the report `review-findings.md`; the quality goal verdict is the coordination session's, made from its disposition of those findings (Composition and verdict > **quality goal**). The contract does not enforce the report's content, so if severity, a finding's judged weight or the head the review saw is missing, ask that session before closing it. Compare the head the review saw with the PR's head. What gets posted on the PR comes from this report, and the report can contain local paths, run commands and the text of the invocation's `instructions`. The module does not decide posting. The default is to condense the report and post only the verdict and findings, leaving out local paths, run commands and the text of the invocation's `instructions`; the workspace's `coordination.md` (if any) and the run's instructions can override this. The review module's reviewers are started by the wrappers of the coordination session's clone of this tool, with the reviewed checkout (the run worktree) as the working directory: `bash <clone>/tools/review/claude-review-pr.sh --pr <n> --out <work folder>/reviews/claude.md [--repo <owner/name>] [--expected-head <branch>] [--records <records>] [--effort <level>]` and `bash <clone>/tools/review/codex-review-pr.sh --pr <n> --out <work folder>/reviews/codex.md [--repo <owner/name>] [--expected-head <branch>] [--effort <level>]`, with `<clone>` the absolute path of the clone of this tool the coordination session runs in. The coordination session gives these commands to the review module in its instructions, for the reviewers the workspace's `coordination.md` names, with `--effort` for a reviewer whose effort the run's instructions or that `coordination.md` name (SETTINGS.md > Reviewer settings); what the work session needs to run them is in WORKSPACE.md > `claude-settings.json`.
- **review or quality → re-entry**: a finding re-enters when the coordination session disposes of it as fix (Composition and verdict > **Disposition**); a deferred or rejected finding does not. The modules that take `findings` are analysis, design and build, and where to go is not in the contract. The coordination session looks at what the finding moves. If it is analysis's conclusion, return to analysis; if it is a decision design made, design; for any other implementation, build. After returning, go through delivery and ci on the new head, and check the fix as Composition and verdict > **Checking a fix** sets: for a fix that changes behavior, rerun the evaluations after it with `previous_evaluation` and rerun review with `previous_findings`; for a fix checked on its diff, no evaluation or review is rerun. Findings that repeat the same property with different cases are read as a signal to look at the criteria again rather than to fix one more case.
- **Connecting with steps outside AutoFlow**: if implementation is done outside AutoFlow, there are no delivery and build outputs. Make a file in the contract's format for `ci` and a `pr` param for review, and run them where that head branch is checked out. If the earlier steps were done with AutoFlow, give the same `records` so the earlier work can be read.

## Composition and verdict

The **workflow** is the groups and order to use for this request, where sessions break, the quality goal and the final result. Choose or change a reference from the form of the issue, such as what it changes, who the demand comes from and what is already decided, and from the workspace's `coordination.md` (if any). Present the outline with these grounds to the operator for approval before the run starts; this is the one approval the workflow takes. Leave what was chosen and why in the run record. When the coordination session judges during the run that the workflow must change, it changes it on that judgment, leaves what changed and why in the run record, and goes on without approval.

A **group** is a set of steps that must be gone through together in resolving an issue. Modules are divided so that the coordination session judges and passes between steps. The coordination session can judge to run only part of a group.

The **verdict** is made by the coordination session for each module run. A module runs up to its goal and only gives scores or findings, and a judged weight for a finding where its output gives one; it does not decide whether they are enough. A criterion-decision run gives decisions: the verdict on it is the check of the facts its decision record states (Judgment at each connection > **criterion-reconcile → criterion-decision → analysis**), and decisions that pass it are followed.

- At the first turn end of a work session after it was given a module run, `tools/watch.py`, run in the background (`run_in_background`), writes that module run's end record ([SETTINGS.md](SETTINGS.md) > Progress records): `status` `ended` and the files the work folder holds at that moment under `outputs.files`. The end record is not written again, so files the session writes after that turn end are not in the list; the output is judged from the work folder itself. `ended` says only that the session stopped. Whether the module run reached its goal or stopped, and whether to go on, is read from the output files and judged by the coordination session.
- Whether an output fits the next input, and whether the facts it states (commit, branch, PR, CI and so on) are right, is checked directly with git and gh.
- A module run that stopped because what it was given could not be used (its Exit section names when it stops) and a module run that did not reach the quality goal are different. The first is a matter of fixing the inputs or instructions and running it again; the second is a matter of finding the cause and re-entering, or stopping when the cause is one the system cannot carry out ([Operator boundary](#operator-boundary)). A stop whose cause is the environment, such as a tool or reviewer the module runs being absent or unable to authenticate, is not fixed by changing the inputs or instructions: it goes to the operator report, as Module connection > **Collect across module runs** does for a missing tool.
- **Disposition**: in this document, a finding is each finding and each recommendation of a module run that judges the work: an evaluation (hypothesis, plan, audit, quality) or the review. The criterion-review modules' findings take their own path (Judgment at each connection > **criterion-reconcile → criterion-decision → analysis**, Module connection > **Criterion decisions**). For each finding, the coordination session weighs the weight the module judged it to carry, with the grounds of that judgment, against the cost of fixing it, and disposes of it: fix it when its weight justifies that cost in this change; defer it when it holds but its fix belongs to later work, written in the `deferred` file or split into a separate issue; reject it when it does not hold or its weight does not justify the cost of fixing it. Each disposition is recorded in the run record with the weight, the cost and the grounds that decided it. Two kinds of finding are split into a separate issue as soon as they are disposed of, whatever the disposition, with `tools/issue.py`, and the run goes on: one whose problem would do harm that cannot be undone and that the change neither introduces nor makes reachable or worse, and, of one whose problem the change makes reachable or worse, the cause the change leaves in code it does not change. The issue holds what its readers may see; the rest goes to the operator in the conversation and in the material for the merge review artifact. A repository's own rules for this are in its workspace's `coordination.md`. A finding that would change what a criterion requires is a cause to re-enter the criteria review, with the finding as its input (Judgment at each connection > **criterion-reconcile → criterion-decision → analysis**).
- **A finding without a judged weight**: the coordination session asks the session that produced it for that weight and its grounds while that session is alive (Module connection > **Ask the session**). When the session is closed or does not give one, the coordination session judges the weight itself from the finding and its grounds, and records in the disposition that the weight is its own judgment.
- **A score**: a score is disposed of through the findings that account for it. When a score's reason names a defect that no finding states, the coordination session asks the session that produced it for that finding and disposes of what it gives. When the session gives none, the coordination session takes the defect the reason names as a finding, disposes of it under **Disposition**, and records in the disposition that it composed the finding itself. A score whose reason names no defect and that no finding accounts for is left as it is and does not stop the quality goal.
- The disposition of the findings decides, in light of the quality goal, whether to go on or re-enter. Verdicts, dispositions and their grounds are left in the run record.
- `tools/status.py` reads a step's state from the Verdict cell of the run record's Progress table. A cell that starts with `pass` or `met`, or holds `goal met`, is a pass; a cell that starts with `missed` or `not met`, or holds `goal missed` or `goal not met`, is a fail. The words count in any case, only as whole words, and the earliest one decides. A cell with none of them, an empty one included unless the next bullet shows its row as `awaiting` or `running`, is shown as written up to its first comma, parenthesis or sentence end, with the state `noted`.
- `tools/status.py` matches a Progress row to an invocation by the first word of the row's Module run cell, its leading run of letters, digits, underscores and hyphens, which must equal the module run's name, as `tools/invocation.py` prints it. So a row of a module run starts that cell with the module run's name, as in `review-1`, and an invocation no row matches, or whose row has an empty Verdict cell, is shown as `awaiting` or `running`. A row for work outside AutoFlow does not start with a run's name; when such a row has an empty Verdict cell and is its session's last row, it is shown as `running` while that session works, as `awaiting` once the session is `turn-end`, and as `noted` once the session has exited.

The **quality goal** is set by the reference default, the workspace's `coordination.md` (if any) and the run's instructions, in that order, each later one overriding the earlier. It is judged by the coordination session's disposition of the findings: it is met when every finding of the module runs it covers is disposed of with grounds (**Disposition**) and every finding disposed of as fix is fixed and the fix checked as **Checking a fix** sets. A low score or a finding of a given severity is not by itself a fail; it enters the verdict through its disposition. The goal can be passed to a module in `instructions`, but the verdict is made by the coordination session.

**Re-entry**: when the goal is not reached, return to the step where the cause arose and run again from there; what is run again to check the fix follows **Checking a fix**. Where it returned and the grounds are left in the run record. How many times to go around is judged in light of the quality goal. Feedback from the operator on a PR that changes direction is also a cause for re-entry, and the feedback goes in as an input of the module returned to. Commits made after the PR is opened go through delivery and ci again and are reflected in the same PR.

**Checking a fix**: how a finding disposed of as fix is checked follows the kind of fix. The coordination session judges which kind a fix is and records it, with the check, in the run record.

- A fix that changes behavior (code, a line a tool reads, what an analysis or design output concludes or decides) is checked by running the evaluation or the review again: for a finding against an analysis or design output, the evaluation on that module's rerun output; for a finding against the committed change or the PR, the evaluations after the step returned to and the review, on the new head.
- A fix that does not change behavior (documents, comments, wording) and a trivial fix, one whose whole effect the diff shows, are checked by the coordination session on the diff: it confirms that the diff answers that finding. The evaluations and the review already made stand for the fixed output or commit. A comment that is itself a defect (an exposed credential and so on) is not settled by a diff check; its fix is checked as a fix that changes behavior.
- Either way, a fix to the committed change goes through commit, push and the CI check where the repository has CI.

**Waiting**: waiting for a work session, whether it carries out a module run, work outside AutoFlow, one-off work or the merge, is the coordination session's work. It sets how long to wait to fit the target repository and the work, gives that time to `tools/watch.py`, and ends its turn and waits; the tick timer ([Sessions](#sessions)) runs through the wait. When the time given to `tools/watch.py` passes, it checks the session's state; the session keeps running. A time the module run itself keeps within its work, such as how long to wait for an external check's result, goes in the instructions (`tools/invocation.py --instructions`).

**Instructions** consist of the module's `SKILL.md`, the goal and what the result must keep. `tools/invocation.py` writes them as the module run's instruction file, which names the path of the module's `SKILL.md`, the inputs, the work folder and the instructions; the file's other contents are set in `tools/invocation.py`. That file gives the module run to a new session (`tools/launch.sh --prompt`) or to a running one (`tools/session.py send`, which enters it as one line naming it when it is over the size the terminal module takes). When instructions are specific, the worker spends its effort finding grounds for those instructions rather than looking in several directions. Instructions are written from the module's definition and its inputs, and state concisely only what this module run needs to know beyond those two. The workspace's instructions are what the coordination session runs the run by; a module run is given only what bears on that module's work. Criteria other than the module's defaults (its Default section), and how to start what the module runs, are given with `--instructions`, which the invocation file keeps as `instructions`. An instruction the coordination session writes and enters into a running work session with `tools/session.py send` says what to do, short enough for the size the terminal module takes (`MAX_SUBMIT_BYTES` in `tools/terminals/__init__.py`). The details the work needs are in files the session reads (the issue, the invocation, the run record, or a file written for that instruction), and the instruction names where they are. When an instruction still needs more, send it in parts, one `send` each: a part is taken as soon as it is entered, starting a turn or queued behind the running one, and while the session holds a choice question, `send` enters nothing and gives the part's own text to that question as the answer to every question of its call ([Composition and verdict](#composition-and-verdict) > Questions). So each part is one the session can act on alone, or says that more follows.

**Questions**: when a work session waits at a choice question, the coordination session decides it as any other decision ([Operator boundary](#operator-boundary) > What the coordination session decides). A choice that would change a criterion's content is decided as Judgment at each connection > **criterion-reconcile → criterion-decision → analysis** sets. It writes the decision and its grounds as the content of an instruction file, one instruction that states the decision for every question of the call, and gives that file to `tools/session.py send`, which gives it to the question as its answer and prints `ANSWERED` with each question it answered. It then waits with `tools/watch.py` and the baseline it gave the watch that printed `WAITING_INPUT`. When `send` prints `ANSWERED` for a text it did not write as the answer to that call, such as a part sent while the turn ran, that text has become the session's answer: it reads the questions from the lines `send` printed and from the transcript, decides them, and sends the decision with its grounds as the next instruction. When a question is the operator's, it frees the question with `tools/session.py release` and tells the operator. When `send` stops at a question and its reason says the question goes to the operator, the dialog goes to the operator. When `close` stops at a held question, it answers the question with `send` or frees it with `release` before closing the session. A permission prompt is not a question: `send` refuses at it, and it goes to the operator ([Operator boundary](#operator-boundary) > Its limit).

## Sessions

A session is the unit that carries out a group. If it can be carried out independently of the earlier step, use a new session; if it has to continue from it, continue in one session. Even when continuing in one session, the judgment between modules is the coordination session's. A session stops when it finishes one module, and the coordination session gives the next input and goal. A new session is passed only the earlier output and the goal. In a run checkout, one session works at a time.

A work session's places are its run worktree and the work folder of the module run it is carrying out. The files the session writes while it works, and the outputs and temporary files of the commands it runs, go in those places. Where the work makes files outside those places by default, such as a temporary file, the coordination session's instructions to the session name those places, so the session makes no file elsewhere.

When it opens a session, the coordination session reads the workspace's `tools.json` (WORKSPACE.md > `tools.json`), matches each tool's description with the work of the modules that session will run, as it matches outputs to inputs by meaning, and passes the tools it chooses to `tools/launch.sh --tools`. They are added to the session, so they serve every module run of that session; a session continued for a later module keeps the tools it was started with. Without a match, it passes none.

The model and effort of a session started for a module's run, and of a module run that continues in a running session, are set in SETTINGS.md > Module settings.

A work session is closed after its group is finished and the coordination session has judged its output, because a closed session cannot be asked for more work or material. One-off work is done in a new one-off session such as `X1`, started with `tools/launch.sh <run-dir> X1` from `x1-prompt.txt`.

After sending a command, confirm that the intended state was reached. Choose the means of confirmation to fit the command's result (process, transcript, screen, file), and if it was not reached, deal with it on the spot before moving on. Instructing the same session and ending a session are confirmed by `tools/session.py`, which prints the result, so the coordination session acts on that output.

Runs are independent of each other. One coordination session runs one run, changes only its own run's data, checkout and sessions, and only reads those of other runs. Before starting, check overlaps with `tools/check.sh`, and start only when it shows none.

**Tick timer**: when the coordination session starts, it starts one tick timer, a background command (`run_in_background`) that ends after 50 minutes, and keeps it running until its run ends, whatever it is waiting for: a work session (a module run, work outside AutoFlow, a one-off session, the merge session) or the operator. At each tick, it checks the state of the run's work sessions (`tools/status.py`) and starts the timer again. The timer does not set how long a wait lasts: the time given to `tools/watch.py` fits the target repository and the work ([Composition and verdict](#composition-and-verdict) > Waiting). When it ends the run, the coordination session stops the running timer, its background command ([When an issue ends](#when-an-issue-ends)).

Run preparation is done by `tools/prepare.py`, and instructing the same session and ending a session by `tools/session.py`.

Terminal control is required for the coordination session. The terminal a run uses is determined by `tools/prepare.py` and written in `run.env`; if terminals are nested, it is specified with `--terminal`. The supported terminals are cmux and tmux. The coordination screen is at least 110 columns wide and 40 rows high.

## Abnormal states and improving the instructions

**Compare at each step.** Before instructing, set the state expected when this step ends, and when it ends, compare the report with the facts (files, git, gh, transcript, process).

**If they differ, read the situation and judge.** If something differs from what was expected, or a decision has no grounds yet, read the facts to find the cause and the grounds. How to continue is decided by the coordination session; it stops and reports only when the cause is one the system cannot carry out, as in [Operator boundary](#operator-boundary).

**Leave what happened.** Leave what differed and how it was handled in the run record's `What happened`.

**Accumulate and improve.** What holds for every run of the workspace's repository is written in the workspace's `coordination.md`, and whether the same thing repeats is judged from it. A fact found anew in each run, such as a path, is written there as it is and used. A condition of one run, such as the operator's instruction for that run, stays in that run's record and instructions. A bug calls for a code change, and the coordination session judges whether it goes into this issue or a separate one. Anything else may call for a change to the instructions; propose it to the operator as the concept or goal already in them, stated more precisely.

## When an issue ends

Goal: when an issue of a repository worked on through a workspace ends, nothing the run opened is left in an unknown state. What was delivered, what remains and what the run still holds can each be told from the facts, and the tools see the run as it really is.

A run is opened by `tools/prepare.py` and ended by the coordination session, since what ending takes differs per repository and per run. Below is what must be accounted for. The coordination session judges how each item applies to this repository and run, and an item can turn out to need no action.

- **The issue's state against what was delivered**: a merged PR does not by itself mean the issue is finished, and a closing keyword closes the issue on merge however much the PR delivered. What counts is what the issue asks compared with what was actually merged. One issue can take several runs, so a run can end while its issue stays open. Where what remains is tracked is part of this.
- **The work sessions**: which sessions of the run are still alive, and whether anything can still be asked of them. The timing of closing is in [Sessions](#sessions).
- **The run's worktree and branches**: what they hold that exists nowhere else, and what still needs them. A run can leave a worktree under the workspace, a branch in the clone and a branch on the remote, and these are separate things: a worktree shares the clone's refs, so removing it leaves the branch in place. Uncommitted files or an unmerged head can exist only here, and a PR that is still open can still need them for re-entry. `tools/merge.py` deletes the remote branches of the PRs it merged or closed, then removes the worktree and the local branch with `tools/cleanup.py`; for a run that ends without it, `tools/cleanup.py <run-dir>` removes them. `tools/cleanup.py` removes nothing while the worktree holds something that exists nowhere else, and names it; judge what it names before removing anything by hand. `tools/check.sh` works in the run's checkout, so it stops short for a run whose worktree is gone.
- **What the repository asks to follow a merge**: the steps that need no judgment are in the workspace's `merge-plan.json` and done by `tools/merge.py` ([WORKSPACE.md](WORKSPACE.md) > `merge-plan.json`). What else follows a merge is read from that repository's own documents and from the workspace's `coordination.md` (if any).
- **The clone, given other runs in progress**: a run's own data, checkout and sessions are its to change ([Sessions](#sessions)), but the clone is shared with the other runs of the same repository. Every worktree shares its refs. `tools/prepare.py` fetches and starts each worktree from `origin/<base_branch>`, so a new run's worktree does not depend on the clone being up to date. Whether to update it is weighed against what `tools/status.py` and `tools/check.sh` show in progress.
- **The run record**: the record holds how the run ended, including what remains, so that a later coordination session can follow it.
- **The run's `STATE`**: `tools/prepare.py` writes `active` in `run.env`, and no tool changes it afterwards. The tools read only whether it is `active`: `tools/check.sh` lists such runs as possible overlaps, `tools/status.py` shows them by default and `tools/launch.sh` counts the surfaces of those opened from the same coordination surface when placing a new session. `tools/status.py` and `tools/launch.sh` compare the whole value and `tools/check.sh` matches its prefix, so a value such as `closed` is not active to all three. So a finished run left `active` keeps appearing to other runs as in progress, and a run marked otherwise while it still holds sessions or a checkout disappears from their overlap checks.
- **The tick timer**: the coordination session's tick timer ([Sessions](#sessions)) runs until the run ends. When it ends the run, the coordination session stops the running timer, its background command, so no tick follows the run's end.
- **What could not be done or falls to the operator**: some of the above may be refused by a permission or another limit the system cannot carry out, or be one of the operator's decisions, such as the merge ([Operator boundary](#operator-boundary)). These are reported as such, with what is needed, so that the report separates what was done from what was not.

## Operator boundary

The operator decides issue selection, approval of the workflow outline presented before the run starts, policy changes and, per issue, which PR or PRs to accept for merge.

**What the coordination session decides.** Every other decision made during the work, such as how to solve the problem, how far the change goes, a change to the workflow during the run, how findings are disposed and how the run ends, is made by the coordination session with its work sessions, from what they checked (the instructions, the code, the facts), and is left with its grounds in the run record. When a choice comes, the coordination session finds out why the decision is needed and which option is better by investigation and analysis (reading the code and the instructions, running what settles the question), and decides on those grounds. A decision that changes a criterion's content is made by a criterion-decision module run, and the coordination session follows it (Judgment at each connection > **criterion-reconcile → criterion-decision → analysis**).

**Its limit.** When a decision is needed, the coordination session first determines whether the problem is one the system cannot carry out: a tool, permission or environment it cannot obtain. If so, it stops, leaves the reason and what is needed in the run record, and reports them to the operator. Otherwise it finds a way to decide and decides.

The operator judges from the conversation with the coordination session and the merge review artifact.

- **Run record**: leaves verdicts, dispositions, re-entries, inputs the coordination session made and their grounds, and what happened.
- **Merge review artifact**: provided with the request for the merge decision, for the judgment. It is made with the `pr-postcard` skill, in a one-off session so that run context does not mix in, and that session is given the locations of the supporting material.

**The merge decision and the merge.** The decision names the accepted PRs (one of several independent attempts can be the one) and the PRs of the issue not chosen, and it holds for each accepted PR's head at the time of the decision. It is given as the approval record, and what the operator does for it is in [README.md](README.md) > First run.

1. The coordination session asks for the decision and gives the operator the command: `PYTHONPYCACHEPREFIX="$(mktemp -d)" python3 <clone>/tools/approve.py <run-dir> --accept <owner>/<name>#<n>@<reviewed head> ... --close <owner>/<name>#<n> ...`, with `<clone>` the absolute path of the clone of this tool the coordination session runs in, and the heads the merge review artifact showed. The coordination session does not write the record, and keeps the operator's words verbatim in the run record. A new decision after a partial merge names the PRs already merged too, at the heads they were merged from.
2. The coordination session starts a one-off session with `tools/launch.sh <run-dir> <name> --without-autoflow` and has it run `python3 <clone>/tools/merge.py <run-dir>`, the same clone's tool by absolute path, as a Bash call of exactly that form. That session can run `tools/merge.py` again, after a `STOP` too; the coordination session therefore closes the merge session as soon as it has read its first result, so that the cause of a `STOP` goes back to the operator. The tool removes the run's worktree, where the session started, so the session is given nothing after it.
3. The coordination session reads the result from the tool's last line and `<run-dir>/merge.log`, and checks the merges, the closed PRs and the removed branches with gh and git. It compares the approval key's fingerprint that `merge.log` names with the one `tools/approve.py --init` printed to the operator, which it asks the operator for, and reports a mismatch to the operator.

A stop of `tools/merge.py` goes to the operator, whose decision the merge carries out, with its `STOP` reason and the decision it needs: a new decision on a moved head, or a rerun once the cause is resolved. A rerun continues from where the tool stopped.

What to confirm with the operator about the base and workspaces is set by [SETTINGS.md](SETTINGS.md) and [WORKSPACE.md](WORKSPACE.md).

## Tools

- `tools/config.py [key]`: the applied settings ([SETTINGS.md](SETTINGS.md)).
- `tools/modules.py`: the listing of the modules, as JSON ([SETTINGS.md](SETTINGS.md) > Module locations; the table above).
- `tools/prepare.py <workspace> <issue> [--key <key>] [--base-confirmed] [--terminal <name>]`: prepares a run, making its run data `<runs>/<run name>/` and `run.env`.
- `tools/invocation.py <run-dir> <module> <inputs-json> [--instructions <text>]`: a module run's name, work folder, invocation and instruction file ([Module connection](#module-connection), [Composition and verdict](#composition-and-verdict) > Instructions), for a module of the run's `MODULES` or `USER_MODULES`.
- `tools/launch.sh <run-dir> <k> [tab] [--prompt <file>] [--tools <name>[,<name>...]] [--model <model>] [--without-autoflow]`: starts the session. Its first message is the module run's instruction file `--prompt` names; without `--prompt`, `<run-dir>/s<k>-prompt.txt`, which the coordination session writes for a session that starts without a module run. `--tools` is stated in [WORKSPACE.md](WORKSPACE.md) > `tools.json`, and the choice of its names in [Sessions](#sessions). `--model` is stated in [SETTINGS.md](SETTINGS.md) > Module settings. When the session's settings are not in effect, the launch fails, naming why and showing the screen: the coordination session closes that session, does not give it work, and launches it again once the cause is cleared (for a start dialog such as folder trust, once the operator has accepted it). `--without-autoflow` starts the merge session ([Operator boundary](#operator-boundary)).
- `tools/module_settings.py <instruction file> [--model <model>] [--without-autoflow]`: the model and effort flags `tools/launch.sh` would give the session of that launch, without starting it ([SETTINGS.md](SETTINGS.md) > Module settings).
- `tools/criteria.py <run-dir> read | seen <last line | none> [--drop <line>] ... | append --grounds <file> [--drop <line>] ... <spec> ...`, a spec being `--revise N <text> <reason>`, `--withdraw N <reason>` or `--add N <text> <reason>`: the criteria block of the run's issue ([Module connection](#module-connection) > **Criterion decisions**). `read` prints the effective criteria, computed from trusted lines, each line's attribution from the issue's edit history, and the difference from `seen`. `seen` records the current state as accepted. `append` posts one grounds comment from the grounds file, with `Run record: <run name>` added, and writes the lines of its specs. An `append` call can last several minutes: the coordination session gives it a timeout that covers this or runs it in the background (`run_in_background`).
- `tools/issue.py <run-dir> --key <key> --title <title> --body <file> [--repo <owner/name>]`: registers a finding as an issue once, finding it instead when the run record or an open issue already holds its key ([Composition and verdict](#composition-and-verdict) > Disposition).
- `tools/watch.py <run-dir> <k> [baseline] [timeout]`: the end record ([Composition and verdict](#composition-and-verdict)).
- `tools/session.py <run-dir> <k> send <file>`: the next instruction to the same session, an instruction the coordination session wrote or a module run's instruction file ([Composition and verdict](#composition-and-verdict) > Instructions), or the answer to the choice question the session waits at: while the session holds a choice question, the file's own text is given to every question of that call as their answer when it fits `MAX_SUBMIT_BYTES`, and otherwise `send` refuses and enters nothing ([Composition and verdict](#composition-and-verdict) > Questions).
- `tools/session.py <run-dir> <k> release`: frees the choice question the session holds, for the operator, and prints `RELEASED` ([Composition and verdict](#composition-and-verdict) > Questions).
- `tools/session.py <run-dir> <k> close`: ends the session ([Sessions](#sessions)).
- `tools/check.sh <run-dir>`: prints other active runs under the root, each module run of the record folder that has an end record with its status and the number of files its work folder held at that turn end, the checkout's tree, and leftover browser, db and server processes ([Sessions](#sessions)).
- `tools/approve.py --init | <run-dir> --accept <pr>@<head> ... [--close <pr> ...]`: run by the operator in their own terminal, never by a session: makes the approval key, or the signed approval record of the merge decision ([Operator boundary](#operator-boundary)).
- `tools/merge.py <run-dir> [--ci-timeout S] [--ci-start S] [--poll S]`: the merge ([Operator boundary](#operator-boundary)).
- `tools/review/claude-review-pr.sh`, `tools/review/codex-review-pr.sh`: the reviewer wrappers, with the reviewer settings of [SETTINGS.md](SETTINGS.md) > Reviewer settings ([Judgment at each connection](#judgment-at-each-connection) > **delivery, ci → review**).
- `tools/cleanup.py <run-dir>`: removes the run's worktree and local branch, and nothing while anything exists only there ([When an issue ends](#when-an-issue-ends)).
- `tools/status.py [run] | --caller [--terminal <name>]`: prints a run's worktree and record folder, module flow, current step, each step's work folder and the status of its end record, the Verdict and Notes cells of the row a step comes from, work session states and the coordination session's surface as JSON. Without arguments, all active runs; `--caller` limits them to the runs made in the calling surface, and is an error if that surface cannot be told.
- `tools/usage.py <run-dir> [COORD=<session-id>]`: totals tokens and cost.
- `tools/terminal_check.py [--terminal <name>]`: the conformance test of a terminal module.

## Language

- Conversation and artifacts are written in the operator's language.
- Everything else is English by default: tools, tool output, run records, instructions to work sessions, instruction documents, a workspace's `coordination.md`, and status displays such as the run-status pane. Text pushed to git (commits, PRs, issues) is in English where possible.
- A run record's `Operator's instruction, verbatim` line keeps the operator's original language.
