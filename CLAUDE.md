# coordination — where the coordination session works

A session opened in this directory is a coordination session. It builds a workflow that fits the request, opens work sessions in terminal surfaces that do the work by running AutoFlow modules, judges the results and connects them to the next module.

- Principle: mechanical behavior runs without AI, through JSON settings and tools. Judgment belongs to the coordination session. The rules state concepts and goals, and the coordination session judges each case by them
- Work records of earlier runs: [RUN-HISTORY.md](RUN-HISTORY.md). Read them as material for improvement work; procedures, rules and grounds come from the documents listed here
- The role of the coordination session (module assembly and connection, verdict and composition, sessions, abnormal states and improving the instructions, what needs handling when an issue ends, the boundary with the operator): [COORDINATOR.md](COORDINATOR.md). Reference workflows: [workflows/README.md](workflows/README.md)
- Settings and paths: [SETTINGS.md](SETTINGS.md). The applied values are read from `tools/config.py`. The work space is the workspaces and run worktrees under the base, and the progress records are `runs` and `records` under the coordination root
- workspace: when presenting workspaces to the user, the coordination session finds the directories that have a `repo.json` in the base the settings point to. When given a workspace, it checks `repo.json`, and reads and follows `coordination.md` if there is one. If the given workspace does not exist, it builds one through questions and answers with the operator, the token included. Every session of a workspace uses only that workspace's `gh-token` as `GH_TOKEN`; the coordination session is started with it (WORKSPACE.md > `gh-token`). The structure, the role of each file and how to find them are in [WORKSPACE.md](WORKSPACE.md). Use a base the user has confirmed: when the base comes from the built-in default, confirm it with the operator before using it (SETTINGS.md > Work space)
- Tools: `tools/config.py [key]`, `tools/prepare.py <workspace> <issue> [--key <key>] [--base-confirmed] [--skip-version-check] [--terminal <name>]` (prepares a run; stops without creating it when `VERSION` without `-rcN` differs from the installed AutoFlow version, or when the workspace's `gh-token` is missing or empty or is not this session's `GH_TOKEN`), `tools/invocation.py <run-dir> <module> <out> <params-json> <inputs-json> [--instructions <text>]` (writes the invocation file and the instruction file. The instruction file is `<out>-prompt.txt`, and `tools/launch.sh` reads `s<k>-prompt.txt`), `tools/launch.sh <run-dir> <k>` (starts the session with the workspace's `gh-token` as `GH_TOKEN`), `tools/watch.py <run-dir> <k> [baseline] [timeout]` (`run_in_background`), `tools/session.py <run-dir> <k> send <file>` (the next instruction to the same session), `tools/session.py <run-dir> <k> close` (ends the session), `tools/check.sh <run-dir>`, `tools/status.py [run] | --caller [--terminal <name>]` (prints a run's worktree and record folder, module flow, current step, each step's output folder and result status, the Verdict and Notes cells of the row a step comes from, work session states and the coordination session's surface as JSON. Without arguments, all active runs; `--caller` limits them to the runs made in the calling surface, and is an error if that surface cannot be told), `tools/usage.py <run-dir> [COORD=<session-id>]` (totals tokens and cost), `tools/terminal_check.py [--terminal <name>]` (the conformance test of a terminal module)
- Run data: `<runs>/<run name>/` (made by `tools/prepare.py`). User values go in the settings files (SETTINGS.md), and each repository's values and instructions in its workspace (WORKSPACE.md)
- A work session is closed with `tools/session.py` after its group is finished and the coordination session has judged its output. One-off work is done in a new one-off session such as `X1`, started with `tools/launch.sh <run-dir> X1` from `x1-prompt.txt`

## Language

- Conversation and artifacts are written in the operator's language.
- Everything else is English by default: tools, tool output, run records, instructions to work sessions, instruction documents, a workspace's `CLAUDE.md` and `coordination.md`, and status displays such as the run-status pane. Text pushed to git (commits, PRs, issues) is in English where possible.
- A run record's `Operator's instruction, verbatim` line keeps the operator's original language.
