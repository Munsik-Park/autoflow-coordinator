# coordination — where the coordination session works

A session opened in this directory is a coordination session. It does not do the work itself. It builds a workflow that fits the request, opens work sessions in terminal surfaces to run AutoFlow modules, judges the results and connects them to the next module (Munsik-Park/autoflow#471).

- Principle: mechanical behavior runs without AI, through JSON settings and tools. Judgment belongs to the coordination session. Do not list or add rules case by case
- Work records of earlier runs: [RUN-HISTORY.md](RUN-HISTORY.md). These are records of progress collected for improvement work, not procedures, rules or grounds. Absorbing their content into rules is done in #4
- The role of the coordination session (module assembly and connection, verdict and composition, sessions, abnormal states and improving the instructions, the boundary with the operator): [COORDINATOR.md](COORDINATOR.md). Reference workflows: [workflows/README.md](workflows/README.md)
- Settings and paths: [SETTINGS.md](SETTINGS.md). The tools hold only the order in which settings are found, and the applied values are shown by `tools/config.py`. The work space is the workspaces and run worktrees under the base, and the progress records are `runs` and `records` under the coordination root
- workspace: no list is kept. When presenting workspaces to the user, the coordination session finds the directories that have a `repo.json` in the base the settings point to. When given a workspace, it checks `repo.json`, and reads and follows `coordination.md` if there is one. If the given workspace does not exist, it builds one through questions and answers with the operator. The structure, the role of each file and how to find them are in [WORKSPACE.md](WORKSPACE.md). Do not work with a base the user has not confirmed (SETTINGS.md > Work space)
- Tools: `tools/config.py [key]`, `tools/prepare.py <workspace> <issue> [--key <key>] [--base-confirmed] [--skip-version-check] [--terminal <name>]` (prepares a run, compares the supported version), `tools/invocation.py <run-dir> <module> <out> <params-json> <inputs-json> [--instructions <text>]` (writes the invocation file and the instruction file. The instruction file is `<out>-prompt.txt`, and `tools/launch.sh` reads `s<k>-prompt.txt`), `tools/launch.sh <run-dir> <k>`, `tools/watch.py <run-dir> <k> [baseline] [timeout]` (`run_in_background`), `tools/session.py <run-dir> <k> send <file>` (the next instruction to the same session), `tools/session.py <run-dir> <k> close` (ends the session), `tools/check.sh <run-dir>`, `tools/status.py [run] | --caller [--terminal <name>]` (prints a run's module flow, current step and work session states as JSON. Without arguments, all active runs; `--caller` limits them to the runs made in the calling surface, and is an error if that surface cannot be told), `tools/usage.py <run-dir> [COORD=<session-id>]` (totals tokens and cost), `tools/terminal_check.py [--terminal <name>]` (the conformance test of a terminal module)
- Run data: `<runs>/<run name>/` (made by `tools/prepare.py`). This repository holds only rules (CLAUDE.md, COORDINATOR.md, workflows, the settings document, the workspace guide, tools), the work records of earlier runs and the version (`VERSION`, [VERSIONING.md](VERSIONING.md)). It holds no user values or individual repository matters
- A work session is closed with `tools/session.py` after its group is finished and the coordination session has judged its output. One-off work is done in a new session in an X surface
